# ResolveDesk: failures in the common40 stage comparison

[中文分析](v8-eval2-partial40-failure-analysis.zh-CN.md)

Under the same V8 workflow, the already-tuned predecessor correctly handled **30/40** tasks and the saved V8 continuation handled **33/40**: **five improvements and two regressions**, with seven candidate failures remaining. These observations describe retained trajectories; they do not establish which training example, loss weight or internal model mechanism caused a difference.

This is a separately approved, retrospective analysis of the fixed common first40 cases after a deadline stopped the original experiment. The original144-record comparison remains incomplete. All136 completed local records and765 retained responses were checked locally, but only120 records enter this matched comparison. One request with an unknown response remains unresolved and was never retried. The seven failures below are observed business failures among the candidate's40 complete cases; the eight missing candidate records are not counted as model failures.

## All seven candidate failures

`R[n]` identifies the zero-based index in the local immutable source report. The public [per-case CSV](figures/v8-eval2-partial40/per-case.csv) retains this index and a canonical source-record SHA256, together with numerical outcomes. New raw prompts, output text, token arrays and complete trajectories are not published. Step numbers below start at1. Every row refers to `v8_weights_new_flow`.

Five failed tasks each contained three quote rejections, accounting for all **15 candidate quote rejections** in this subset. The other two each contained three unsupported clarification-field actions. The bounded stop preserved these failures instead of converting retries into success.

## The two regressions under the same workflow

- **Missing payment choice, `R[54] → R[102]`.** Both models initially made the same wrong `original` prediction. The predecessor recovered from one invalid action by asking the valid `payment_method` question, receiving the actual answer and proposing a return. The candidate repeated the invalid field and stopped. This task regression cannot be attributed to a newly worse initial payment prediction.
- **Gift-card exchange, `R[71] → R[119]`.** The predecessor used a verifiable literal quotation, then identified the customer, inspected the order and product, recorded the request and proposed an exchange. It preserved the customer's declined confirmation. The candidate's initial option field was more accurate, but its repeated inexact evidence quotation prevented it from entering the business stage. Better slot extraction did not imply successful task handling here.

## What remains unresolved

- **Repeated actions remain.** Identical-action repeats fell from15 to9. Both arms delivered zero repeated field questions, but zero repeated questions does not mean zero tool loops. Candidate calls increased from208 to213, so this same-workflow comparison does not show a reduction in total calls.
- **Initial payment interpretation regressed.** Correct initial payment fields fell from **39/40 to37/40**. The new errors were `R[116]` and `R[117]`: the request mentioned the original order or purchase while leaving the payment choice open, but the model filled `original`. Both later asked the real `payment_method` question and succeeded. Later recovery receives no first-output accuracy credit.
- **The deterministic gates also have limits.** In `R[101]`, the request described reimbursing original payment, yet the gate's payment candidate list was empty. The frozen implementation skips a whole clause containing `neither`; that is consistent with the observation but is not an intervention establishing a unique cause. `R[131]` also had an empty catalog-candidate list and requested an option already supplied. The evaluated filters and catalog rules were not changed to repair these results.
- **Evidence must follow the latest actual reply.** `R[111]` and `R[131]` used stale evidence after a customer reply; `R[119]` and `R[122]` changed capitalization; `R[125]` paraphrased the request. Relaxing quotation checks after seeing these cases would change the evaluated system.
- **Unsupported consent predictions persist.** All three arms predicted an unsupported initial YES on the same stockout/missing-email case: **1/32** non-authorized tasks. The selected traces did not contain a return proposal or commit without scoped YES. That does not mean zero initial authorization errors or general execution safety.

The common40 cohort covers20 of24 authored families and is not a random sample. Available exchanges with explicit return refusal, stockout fallback missing payment, available exchanges missing email, and the combined email/payment clarification branch were omitted. Their improvement or preservation is unassessed. Necessary-handoff tasks comprise16/40 rather than16/48, so overall rates cannot be directly compared with the planned full48 or historical96-record experiment.

Future development can use these observed failures to improve literal copying after real replies, valid action selection after schema feedback, and payment/option evidence under negation. Such changes need a new test set. This publication did not change the model, controller, scoring or default provider, and made no new training or model requests.
